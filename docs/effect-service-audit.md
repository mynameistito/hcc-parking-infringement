# Effect service-design audit

Snapshot: 6 November 2026. HCC pagination now uses an Effect service and transport port. The inventory below records current boundaries and conditional future opportunities; it does not prescribe a wholesale migration. This inventory groups related authority sites by owning capability. Findings are recommendations, not evidence that Promise-based or framework code must be migrated wholesale.

## Priorities

1. **HCC pagination and transport — implemented at the existing boundary.** `hcc-pagination.ts` owns `HccClient`, `makeHccClient` and its dependency-preserving layer. The constructor acquires `HccTransport` for page requests; `hccClientLayer` requires `HccTransport` and provides `HccClient`. `hcc-client.ts` owns the HTTP adapter and assembles that layer at the Promise boundary used by the current Worker, queue and CLI callers. The adapter's module-level limiter retains its existing shared lifetime across calls. Direct Effect consumers can supply the transport explicitly. If those workflows become Effect-native, move composition to their owning roots rather than providing inside their operations. The transport-injection and failure-order tests cover the service seam; existing request tests cover cancellation and the shared limiter.

2. **P1 — seed-object authority once refresh is Effect-native.** `live-seed-refresh.ts` reads and writes objects through `seed-r2-client.ts` and also fetches HCC data; `SeedParkingStoreReader` reads the same seed. Binding versus S3 credentials, caching and I/O are currently chosen through `SeedR2Env` at each operation. A narrow seed-object port beside the operations, with an R2/S3 adapter owning its configuration and cache, would make this authority visible when migrating this workflow. Keep object keys and manifest parsing as values. Supply the adapter at the Worker/DO root; use real local protocol/binding tests for storage and caching, extending `seed-r2-client.test.ts` and `server/__tests__/live-seed-refresh.test.ts`. Do not call a partial fake a memory implementation. A dependency-preserving layer and production assembly belong with the port and adapter respectively; no general-purpose storage service is needed.
3. **Keep operation-time handling.** `live-seed-refresh.ts` captures one instant for related windows while retaining actual completion timestamps. `hourlySync` in `sync-window.ts` reads one date before deriving both window boundaries; `sync-backfill.ts` likewise captures one date for its end boundary. No repeated clock read within either operation was found. If these workflows become Effect-native, Effect Clock can supply the instant at their boundary; deterministic date calculations remain values.

4. **P2 — review app scope only alongside a real Effect conversion.** `app-scope.ts` bundles raw `Env`, `ParkingStoreReader`, mode and cache; `app.ts` creates it per request, `worker.ts` for scheduled work, and `backfill-queue.ts` for queue work. The reader interface already represents a real alternative between seed and DO; the scope also leaks raw bindings to application functions. When a caller is converted, yield a narrow reader/write capability and provide its adapter at the Hono/scheduled/queue root. Preserve per-request cache lifetime and seed/DO selection. Do not replace this with a service merely to rename the existing bag. Validate both reader implementations and the public endpoints, including `parking-reader/seed-reader.test.ts`.

## Audit limits

Searches covered `src` and `scripts` for Effect tags/layers/provision, direct fetch, environment, clocks, timers, persistence and browser/runtime bindings, and traced representative entrypoints. Re-run the inventory before implementing further findings. This is a capability-level inventory, not a statement that every individual SQL query, event callback, or UI hook was independently traced. The repository pins Effect 4 beta; verify the installed version's platform services and APIs before selecting a concrete Layer shape. No tests were run specifically for this documentation-only audit.
